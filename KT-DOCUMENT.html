1. Project Overview & Tech Stack

What it is: A mobile-first Progressive Web App used by BBNL franchisees and field agents to run day-to-day CRM operations — onboarding customers with KYC, taking payments, managing tickets on a map, and provisioning four services (Internet, Cable TV / IPTV, Voice, Fo-Fi Smart Box). It doubles as a customer self-service portal with Live TV (275+ channels) and an OTT hub.

Two personas, one app. localStorage.loginType is either franchisee (employee/operator) or customer. That single flag switches the dashboard, the bottom navigation, and the appkeytype header sent on every API call.

Production base path is /smartphone/crm/. It is baked into the Vite base, the router basename, the PWA manifest scope/start_url, the service-worker registration scope, the generated .htaccess, and server.js (BASE_PATH). Changing it breaks every already-installed PWA on users' phones. Treat it as immutable.

5. Bootstrap & Application Architecture

Startup sequence (src/main.jsx, in order)

1. import api-connectivity-test — dev reachability probe 2. cleanupStalePWA() — unregister service workers left by other apps on this origin; may trigger a reload 3. setupPwaNavGuard() — in standalone mode, send external links to the system browser 4. navigator.storage.persist() — ask Android not to evict our caches 5. import channelStore — self-hydrates IndexedDB (L2) → memory (L1) 6. import iptvPrefetch — background channel/language/logo warm-up 7. controllerchange listener — new SW activated → reload once 8. cacheHealthCheck() — compare stored build ID vs VITE_APP_BUILD_ID; on mismatch purge `app-assets` + `workbox-precache` and reload once 9. visibilitychange listener — print the API perf report when backgrounded 10. ReactDOM.createRoot(...).render(...)
One reload, ever. Four independent mechanisms can want to reload the page after a deployment (stale-PWA cleanup, cache health check, SW controllerchange, chunk-load failure). They all funnel through a single reloadScheduled flag plus a sessionStorage guard, so a user can never land in a reload loop. Preserve this invariant if you touch main.jsx.

Provider stack

<React.StrictMode>
  <ErrorBoundary>              // chunk/render errors → purge caches, reload once
    <ThemeProvider>            // dark/light
      <AuthProvider>           // session (7-day TTL), login/logout side-effects
        <ToastProvider>        // app-wide toasts
          <BrowserRouter basename="/smartphone/crm/">
            <App />            // → BrowserGate → AppRoutes
          </BrowserRouter>
        </ToastProvider>
      </AuthProvider>
    </ThemeProvider>
  </ErrorBoundary>
</React.StrictMode>

BrowserGate

App.jsx wraps all routes in BrowserGate. In a normal browser tab it refuses to render the app and instead shows an install prompt (or a thank-you screen once installed). It only lets the app through in standalone/PWA display mode or when import.meta.env.DEV is true — which is a Vite built-in that is false in every build, so the gate cannot be bypassed in a deployed bundle. If a stakeholder says "the deployed link just shows an install screen in Chrome", that is the gate working as designed.

State management

No Redux, no Zustand. React Context for auth + theme + toasts, component-local state everywhere else, and three custom stores: channelStore (IndexedDB), logoCache (blob URLs), lsCache (localStorage with TTLs).

Expiry & logout both clear the same things

On expiry (> 7 days) and on explicit logout, AuthContext clears the session keys, calls lsClearAll() (every _c: cache entry), and deletes the registration draft keys: register_form_draft, registrationData, photoFileId, addrproofIds, idcardIds, filerefid.

Why the draft keys matter: without clearing them, the next operator to log in on a shared field phone would see the previous operator's half-finished "Add User" form — including uploaded document IDs. This survived PWA reinstall on Android WebView. If you add a new draft key, add it to both the logout and the expiry branch.

8. API Layer — Cross-Cutting Behaviour

There is no single HTTP client. Each service file has its own apiFetch-style wrapper, but they share the same design. generalApis.js is the reference implementation.

Standard headers

{
  "Authorization": VITE_API_AUTH_KEY,
  "username":      VITE_API_USERNAME,
  "password":      VITE_API_PASSWORD,
  "appkeytype":    loginType === "franchisee" ? "employee" : "customer",
  "appversion":    "1.2.0",
  "X-App-Package": "com.bbnl.smartphone",
  "Content-Type":  "application/json"        // omitted for multipart uploads
}

Note the credentials are app-level, shipped in the bundle — they are not the end-user's credentials. The user is identified by payload fields (userid, loginuname, apiopid, …).

What every wrapper gives you

BehaviourDetail
DeduplicationA module-level Map keyed by URL+body. Concurrent identical requests share one Promise. Prevents the "three components mount, three identical 6-second calls" pattern.
TimeoutsAbortController. General 30 s, uploads 60 s, orders 15 s, registration 15 s (payments 45 s), Fo-Fi 30 s (60 s for the known-slow calls), IPTV adaptive 12–25 s by connection type.
Navigation abortEvery non-background request links to navigationController's signal. Changing service page aborts the previous page's in-flight calls instantly (§11).
Perf trackingperfMonitor.start(method, url, category, label) → end({status, size, cached}). Feeds window.__apiPerf.
Security logging401/403 emit logger.security("API_AUTH_REJECTED", …).
CachingRead-mostly endpoints check lsCache first and accept a skipCache boolean to force a refresh.
30-second general timeout is deliberate. The previous 15 s cap produced constant "Request timed out" errors on low-tier franchisee phones on 3G, where DNS + TLS + server RTT + retransmits routinely exceed 10 s before a byte arrives. Don't lower it without field data.

10. Caching Architecture

┌─ IPTV data (channels / languages / ads) ────────────────────────┐ │ L1 channelStore in-memory Map ~0 ms │ │ L2 IndexedDB `iptv-store` 2–5 ms, persistent │ │ L3 Service Worker `iptv-api-v1` POST SWR, 7-day max │ │ L4 Network │ └─────────────────────────────────────────────────────────────────┘ ┌─ CRM data (customers, plans, boxes, tickets) ───────────────────┐ │ lsCache — localStorage, `_c:` prefix, per-call TTL │ └─────────────────────────────────────────────────────────────────┘ ┌─ Images ────────────────────────────────────────────────────────┐ │ logoCache (blob: URLs) → Workbox `channel-assets-v4` (CacheFirst)│ └─────────────────────────────────────────────────────────────────┘

lsCache.js — the CRM cache

  • Every key is namespaced _c:; entries are { d: data, t: timestamp }.
  • lsGet(key, ttl) → data or null. lsGetStale(key, ttl) → { data, fresh } for stale-while-revalidate rendering (this is how service pages paint instantly and refresh behind the scenes).
  • lsSet evicts oldest entries on QuotaExceededError. lsRemoveByPrefix supports targeted invalidation. lsClearAll wipes the namespace (called on logout/expiry).
  • On first access it lazily deletes expired entries and migrates away from the old un-prefixed key names (walbal_, custlist_, tkts_, …).

channelStore.js — IPTV L1 + L2

  • IndexedDB iptv-store, object store data. Self-hydrates L2 → L1 on import (_hydratePromise, ~5 ms); waitForHydration() / isHydrated() let callers avoid a flash of empty list.
  • Base freshness 30 min, extended on slow connections via getAdaptiveTTL(); language lists get double the TTL.
  • 275+ channels with logos is far too much for localStorage — that is why this exists. Do not "simplify" it into localStorage.

logoCache.js — channel logos

  • L1 map of source URL → blob: object URL; L2 is Workbox's CacheFirst channel-assets-v4.
  • Concurrency scales with the connection: 2G ≈ 6, 3G ≈ 30, 4G ≈ 100 parallel fetches. Language logos jump a priority queue.
  • Failures: 2 retries, 60 s cooldown, and a sentinel distinguishing "404, never retry" from "transient, retry later".

sw-api-cache.js — POST caching in the service worker

Workbox only caches GET. IPTV uses POST for channel/language/ad lists, so this custom importScripts'd handler runs before Workbox's router and implements stale-while-revalidate for those endpoints: fresh (< TTL) → serve cached, no network; stale (< 7 days) → serve cached and revalidate; network failure → serve stale. Fresh-TTL is connection-aware (2G 60 min / 3G 30 min / 4G 15 min, doubled for the language list).

11. Prefetch & Navigation Control

Two small modules solve a real field problem: the backend is slow (see §25), and browsers allow only ~6 concurrent connections per origin. Without coordination, a page you just left keeps hogging the pipe from a page you just opened.

navigationController.js

  • refreshServiceController() — called at the top of each service page's fetch effect. Aborts all previous in-flight page requests and issues a fresh signal.
  • getServiceSignal() — apiFetch and fofiApiFetch link every request to it, so navigation cancels them automatically.
  • enterBackgroundMode() / exitBackgroundMode() — prefetch wraps its calls in these so warm-up requests are not aborted on navigation. That is the whole point of prefetching.

prefetch.js — customer cache warm-up

  • prefetchCustomerData(userid, logUname) — light, common warm-up when the operator opens a customer.
  • prioritizeCustomerService(userid, logUname, serviceKey) — when a service tile is tapped, that service's data is fetched first; the broader prefetch resumes ~3 s later (POST_SELECTION_PREFETCH_DELAY), and deferred work waits 5 s (DEFERRED_PREFETCH_DELAY).
  • invalidateIptvServiceStatusCache() — drops all box/plan/customer-detail cache prefixes (cabletv_boxid_, cblcust_, pricust_, uai_*, plandets_*, iptvLastSub_). Called on login, so a new operator never inherits the previous one's cached box state.
  • TTLs: overview 2 min, plans 10 min, resolved box ID 1 year (a box ID never changes).

iptvPrefetch.js

Runs at startup and again on login. If cached IPTV data is fresh it only preloads language logos; if stale it fetches languages + channels in parallel, stores them in L1/L2, and prefetches the public IP that the stream API requires.

13. Fo-Fi Smart Box (deep dive)

src/pages/services/FoFiSmartBox.jsx is 5,346 lines — the single most complex file in the repo, and where most recent bug-fixing has happened. Read this section before touching it.

The three views

ViewPurpose

Box identity — utils/boxId.js is the only authority

Different backend classifications nest the same box under different servkey buckets (fofi, multi, voip, internet). extractBoxFromItem() decides what counts as a box, and there is deliberately no "any non-empty field" fallback. A plain cable-TV smartcard/STB identifier with no BBNL/FoFi marker is not a Fo-Fi box. A previous loose fallback made cable-TV-only customers show a phantom "FoFi Box ID" on the Cable TV overview while the Fo-Fi page correctly said "not opted". Keep the decision in this one file — IPTVService, FoFiSmartBox and prefetch all call into it precisely so they can never disagree.

Recognition patterns: BBNL-ANDBOX-* / BBNL_* box IDs, FOFI###### serials, MAC addresses, and the FTA identity described in §25. detectLinkedTvType() separately recognises Android TV / Samsung (Tizen) / LG (webOS) — these carry no BBNL-format ID and need their own identity check.

Pending-plan optimism

After a successful payment or upgrade, the backend can take 10+ seconds to propagate the new plan into getMyPlanDetails and the assigned-item buckets. During that window every read still returns the old plan. The page therefore writes the just-purchased plan into sessionStorage keyed by box ID (fofi_pending_plan_<boxid>, 10-minute TTL) and keeps showing it until the backend confirms the same plan. plansEquivalent() compares names tolerantly ("FoFi-Box + FTA ONLY" ≡ "fofibox_fta_only"). Without this, the Current Plan card visibly flaps back to the old plan right after payment.

Device pairing flow

Parallel to this, linkFoFiBox (freeOTAService) handles the OTA-link case and upgradeRegistration handles an existing customer upgrading into Fo-Fi.

Caching on this page

Overview data is read through lsGetStale with a 2-minute TTL so a revisit paints instantly. Link-flow plans keep a 7-day last-known-good copy (LINK_PLANS_LKG_TTL) because specialInternetPlans is slow and occasionally flaky — a stale plan list beats an empty screen.

14. Payments & Payment History

Paynow.jsx — internet payment, and the GST story

The most important billing fact in this codebase. apis/makepayment returns each GST sub-tax rounded to whole rupees: a true CGST of ₹4.58 comes back as 5.00. The real billing engine (internet/paymentinfo and the printed receipt) charges the precise ₹4.58. Trusting makepayment's value inflated the displayed total by ≈₹1, and because that displayed total became the paidamount sent to savePaymentApi, the backend recorded the ≈₹1 difference as a phantom customer Balance Amount that accumulated on every renewal and quietly ate ₹1 of operator wallet per cycle.

How it is handled now. buildStrictInternetRenewal() never reads the rounded tax value. It calls readNestedTaxPerc() to get each sub-tax's own percentage and computeNestedTax() to recompute it against the taxable base:

CGST = round(taxableBase × CGST% / 100, 2)     // same for SGST
taxableBase = subtotal ?? planamt ?? plan rate  // first available, so backend
                                               // discounts are respected

The precise values flow into both the on-screen total and the paidamount, so the customer total now equals the backend invoice exactly. If a percentage or the base is missing, it falls back to the old rounded value — no plan regresses.

If you ever add a new payment screen, do not read taxdetails.subtaxes.*.value directly. Reuse the recompute helpers.

FofiPayment.jsx

Fo-Fi purchase/renewal: service/paymentinfo/fofi → createFoFiPaymentOrder → verifyFoFiPayment (or processFoFiBillPayment for bill settlement) → writes the pending plan → returns to the Smart Box overview with paymentSuccess state.

PaymentHistory.jsx + constants/services.js

apis/custpayhistory returns every payment for a customer regardless of service, so the page has to classify each order itself. resolveServiceFromOrder() does it in four layers:

LayerSignal
0 — authoritative_authoritativeService, stamped by orderApis when the row came from a server-side servid-filtered endpoint (Fo-Fi servid 3 / Cable TV servid 1). Definitive.
A — explicit fieldservicekey, srvtype, service_type, module, category, … (first non-empty wins)
A.5 — coded fieldservid / services_app mapped through the alias table
B — planid bridgea {planid → serviceKey} map built from getMyPlanDetails per service
C — plan-name regexlast resort (/\bfo-?fi\b/, /smart\s*box/, /\biptv\b/, /\bmbps\b/, …)
Unclassifiable orders are kept, not dropped. filterOrdersByService() only removes orders positively identified as belonging to a different service. Showing a stray row is acceptable; silently hiding a payment the operator actually made is not. Preserve this bias.

services_app = 1 is explicitly not mapped, because Internet and IPTV wallet-debit rows both use it — mapping it would misfile real payments.

The page also renders a jsPDF receipt and de-duplicates rows via getStableOrderKey() (order id → txn id → payment id → receipt id).

15. Registration, KYC & Camera

Register.jsx (1.4k lines) is a multi-step operator-driven onboarding: personal details → address (with map picker) → plan → documents → signature → payment.

Validation & submission

Username/email/mobile availability all go through the one ServiceApis/generalValidation endpoint. Documents upload to ServiceApis/custKYC, then registerCustomer (custservregistration) creates the customer, and submitRegistrationNecessities finalises. Draft state is persisted to localStorage under register_form_draft / registrationData and the file-ID keys — all cleared on logout and expiry (§7).

Camera: the low-memory Android problem

On MIUI/Redmi/Xiaomi and some budget Samsung devices, the OS kills the browser tab while the native camera is open, destroying the captured File. Nothing in the web platform prevents that. The mitigation is two-part:

  • PhotoCaptureModal.jsx + hooks/useCamera.js — an in-page camera (getUserMedia → <video> → canvas → JPEG File) that replaces the native <input capture> flow entirely, so the tab never goes to the background. useCamera also installs a legacy getUserMedia shim and enforces timeouts (12 s acquire, 8 s ready) so the "Starting camera…" overlay can't hang forever.
  • utils/cameraPrep.js — isLowMemoryDevice() (MIUI/Xiaomi/Redmi/Poco UA, Samsung A/J/M series, or navigator.deviceMemory ≤ 3) and prepareForCameraCapture(), which clears transient caches, requests persistent storage, and hints the GC before the camera opens. A sessionStorage flag (app_camera_open) lets the page detect that it was killed mid-capture and tell the user, instead of silently losing the photo.

utils/kycRetry.js

Immediately after an operator creates a customer, the backend's operator-entitlement sync lags a few seconds and customer-scoped calls return misleading errors: "Operator is disabled", "You are not a valid user to register", "device not belongs op(…)". These are races, not real failures. loadKycWithRetry() retries only those messages (3 attempts, 3 s apart) and returns anything else immediately, so genuine errors still surface fast.

QRScanner.jsx

jsQR over a getUserMedia stream, hardened for cheap Android hardware: an in-flight guard (two simultaneous getUserMedia calls throw NotReadableError on Samsung/OnePlus/Realme), soft/hard readiness timers, playsinline for iOS, and full track teardown on unmount so a second scan can acquire the camera.

iptvApi.js resilience

  • Dedup: identical concurrent requests share one Promise.
  • Circuit breaker: 3 consecutive 5xx → open for 30 s (fails fast instead of hammering a dead backend).

  • Adaptive timeout: 4G 12 s / 3G 20 s / 2G 25 s, one automatic retry (worst case stays under ~30 s).

22. Performance & Instrumentation

Build-level

  • Manual chunks: hls, maps, pdf, swiper, animations, vendor-react.
  • Modulepreload suppression: modulePreload.resolveDependencies strips preload hints for the heavy chunks. Without it Vite injected <link rel="modulepreload"> for pdf (574 KB), hls (509 KB), maps (146 KB), animations (120 KB) and swiper (68 KB) into index.html, so every page load downloaded ~1.4 MB of JS the user might never need.
  • Downlevel target: ['es2019','safari14','chrome87','firefox78','edge88']. Vite's default target emits syntax that parse-errors on older field devices — the symptom was "loads fine on one phone, blank screen on another". Do not remove this.
  • Console stripping: production drops debugger and treats console.log/debug/info as pure (removable). console.warn/error survive.

Runtime

  • React.memo on IPTV list children; content-visibility: auto and contain: layout style on list rows so off-screen items skip layout/paint.
  • Connection-aware everything: timeouts, cache TTLs, image concurrency (§8, §10).
  • Navigation-abort + prefetch prioritisation (§11).

apiPerfMonitor — how to debug a slow screen

Every API call in every service file is timed. In DevTools console:

It keeps a 500-entry ring buffer (memory-safe on mobile) and aggregates per endpoint: count, avg/p95 duration, status codes, cache hits, connection type. It auto-prints when the tab is backgrounded (in production only if there were errors or p95 > 3 s) and every 2 minutes in dev.

23. Security & Logging

Security posture

  • Stream URLs are XOR + base64 obfuscated in sessionStorage so a tokenized origin URL isn't sitting in plain text in DevTools.
  • No Fullscreen API in the player (CSS rotation instead) so the browser never overlays the origin domain.
  • Stream proxy is gated: origin/referer check + a hostname allowlist (STREAM_HOSTS). Only livestream.bbnl.in and livestream2.bbnl.in can be proxied.
  • Directory-traversal guard in server.js — resolved paths must stay inside dist/.
  • Security headers (HSTS, X-Content-Type-Options, X-Frame-Options, X-XSS-Protection) are set by nginx.
  • Session hygiene: 7-day expiry, full cache + draft wipe on logout/expiry, and invalidateIptvServiceStatusCache() at login so a shared phone never leaks the previous operator's customer state.
Known weakness, by design of the backend contract: the app-level API credentials (VITE_API_USERNAME/PASSWORD/AUTH_KEY) are compiled into the client bundle and are extractable by anyone who installs the PWA. Every request carries them. Fixing this requires a backend token exchange; it is not something the frontend can solve alone. Flag it to whoever owns the API.

logger.js

  • Dev: debug, info, warn, error, security. Production: warn, error, security only.
  • Auto-redacts password, Authorization, x-api-key, token, secret, credit_card, cookie from any logged object.
  • Security events: LOGIN_SUCCESS, LOGOUT, SESSION_EXPIRED, STALE_SESSION_REMOVED, CORRUPT_SESSION_REMOVED, API_AUTH_REJECTED.

The other server files

  • deployment-package/server.js — the deployable server variant (same responsibilities, with gzip).
  • deployment-package/relay-server.js — a standalone edge relay handling only /stream/* with a 200 MB / 30 s segment cache.   • stream-proxy-plugin.js — the same proxy as a Vite dev plugin, so /stream/ works with npm run dev.
  • local-prod-preview.cjs — serves a production build locally with API proxying (more useful than npm run preview when you need real data).

25. Backend Quirks & Known Issues

Backend behaviours you must code around

QuirkConsequence & handling
apis/makepayment rounds GST to whole rupeesThe receipt and billing engine use precise decimals. Recompute from the percentage — never trust the returned value. See §14. billing-critical
Dates come back as DD-MM-YYYYnew Date("03-07-2026") is parsed by JS as March 7 (US locale), so a subscription expiring 3 July looked expired. Always use parseBackendDate() / isExpiredDate() from utils/dateParse.js. It handles DD-MM-YYYY with 12-h am/pm, 24-h, date-only, and true ISO. correctness
getUserAssignedItems and validateBeforeFofiBoxReg take 6–8 sNot a frontend bug. This is why the 30 s timeout, the stale-while-revalidate rendering, the prefetch prioritisation, and the navigation-abort machinery all exist.
ServiceApis/specialInternetPlans returns a bare arrayNo {status, body} envelope like every other endpoint. Parse accordingly.
GeneralApi/cblCustDet fails authentication in productionWorks in the test environment only. In production, read the equivalent data from primaryCustdet → multplatforms.
Post-creation operator-sync raceFor a few seconds after registration, customer-scoped calls return "Operator is disabled" / "not a valid user to register" / "device not belongs op(…)". Retry only these — utils/kycRetry.js.
Post-payment plan propagation lag (10+ s)Reads still return the old plan. Handled by the sessionStorage pending-plan store in FoFiSmartBox.jsx (§13).
FTA boxes have no text markerThey present as a plain hex ID plus an fserialno field. Identity is decided in utils/boxId.js — do not add a loose "any non-empty field" fallback anywhere else (§13).
custpayhistory ignores the serviceIt returns every payment for the customer. Classification is the client's job — constants/services.js (§14).

26. Deployment Checklist

Pre-flight

  • ☐ .env.production present in the project root with the correct credentials (it is not in git)
  • ☐ Node.js 18+ on the build machine and the server
  • ☐ nginx ≥ 1.25.1 (required for proxy_http_version 2.0)
  • ☐ TLS certs at /etc/ssl/certs/bbnl.crt and /etc/ssl/private/bbnl.key
  • ☐ Confirm VITE_API_APP_DIR_PATH is still /smartphone/crm/ — changing it orphans every installed PWA

Build & ship

  • ☐ npm ci && npm run build → dist/ (also emits the service worker, manifest and .htaccess)
  • ☐ Copy dist/ + server.js (or deployment-package/server.js) to the server
  • ☐ Set STREAM_HOSTS in the Node process environment
  • ☐ Start under systemd/pm2: node server.js (port 3000)
  • ☐ sudo nginx -t && sudo systemctl reload nginx

Verify on a real phone, not just curl

  • ☐ curl -I --http2 https://bbnlnetmon.bbnl.in/smartphone/crm/ returns HTTP/2
  • ☐ PWA install prompt appears; installed app opens past BrowserGate
  • ☐ Service worker registers (DevTools → Application → Service Workers) and the old one is gone
  • ☐ Login + OTP → dashboard
  • ☐ Open a customer → all four service tiles load
  • ☐ Run one real payment and confirm the on-screen total equals the receipt and Balance Amount stays 0.00 (§14)
  • ☐ Live TV plays; try a channel with a fresh token
  • ☐ Check __apiPerf.printReport() for anything above ~8 s that isn't a known-slow endpoint
After deploying, existing users' first load will detect the new build ID, purge app-assets + precache, and reload once. That is expected — a single reload, not a loop. If you see repeated reloads, the guard in main.jsx is broken.

02

Why the backend is slow — and why it isn't the app or the network

1 · The test ran without the app. Every figure above came from a standalone Node.js script hitting the production API with the same headers and payloads the app sends. No browser, no React, no service worker — none of the app's code executed. The delays reproduced identically. Code that never ran cannot be the cause.

2 · The server software is seven years past end-of-life. Every response carries the same signature:

HTTP response header · ServerApache/2.4.6 (CentOS) OpenSSL/1.0.2k-fips mod_fcgid/2.3.9 PHP/5.6.40

PHP 5.6 reached end-of-life in December 2018. It predates the JIT compiler (PHP 8) and the large opcode-cache and engine gains of PHP 7. Requests are served through mod_fcgid, an older process model with more per-request overhead than the PHP-FPM setup modern deployments use.

3 · Payload size proves it isn't the network. If a slow connection were the problem, big responses would be slow and small ones fast. The opposite is true here:

validateBeforeFofiBoxReg returns 62 bytes in 1.42s. registrationNecessities returns 70 KB — over 1,000× more data — in 0.96s, which is faster. The wait is the server thinking (database queries, downstream lookups) before it has anything to send, not the wire moving bytes.

03

How efficiently the frontend fetches

The app cannot make the server faster, so it does the next best thing: fetch the minimum, fetch it in parallel, fetch it early, and never fetch the same thing twice. These are the techniques already in the codebase.

1

Request deduplication

Concurrent identical calls (e.g. the prefetch and the page both asking for the same customer) share a single in-flight promise, keyed by URL + body — the request goes to the server only once.

−50% duplicate calls
2

Multi-tier caching with TTLs

Every response is cached in localStorage with a purpose-fit lifetime — plan details 5 min, customer details 10 min, the resolved box ID a full year. IPTV channel data uses a 4-tier cache (memory → IndexedDB → service-worker → network). Repeat views read from cache in ~0 ms.

0 ms on repeat
3

Parallel batching

Independent calls fire together in one Promise.all batch, so a page waits the length of its slowest call, not the sum. Fo-Fi's four bucket lookups cost ~1.46s together instead of ~5.8s.

4 calls → 1× time
4

Connection-order prioritization

The browser opens only a few sockets per server, so the app now initiates each page's critical call first — the Internet plan card before the slower assigned-items and detail calls — so it isn't stuck in the queue behind them.

critical call first
5

Predictive prefetch

The instant a customer is opened, the app quietly warms that customer's data in the background; the instant a service is selected, it warms exactly that service's calls (including Add Fo-Fi Box's eligibility gate). By the time the operator taps, the answer is often already cached.

hides latency
6

Stale-while-revalidate paint

If any cached data exists, the page renders it instantly and refreshes in the background — the operator sees content immediately instead of a spinner.

instant first paint
7

Section-level fast paint

Each section renders the moment its own call returns, rather than the whole page waiting for the slowest one. The plan card appears at ~1.0s even though the full Internet page settles at ~1.5s.

−0.5s perceived
8

Navigation abort

Leaving a page cancels its still-pending requests, freeing the limited connection pool so the next page's calls start immediately instead of queuing behind abandoned ones.

no stale queue
9

Timeouts & retries

Every call is bounded by an AbortController timeout (30s, 60s for uploads) with limited retry on transient mobile-network blips — so a dropped request self-heals instead of hanging.

resilient
10

Built-in measurement

Every call is timed and inspectable at window.__apiPerf in the browser console — the same instrument used to produce this report, so any regression is visible immediately.

observable
04

Why it's still slow despite clean fetching

All ten techniques above reduce how often and how many calls are made. None of them can reduce how long a single call takes once it has to hit the server. That server floor is the residual slowness.

What the frontend removes

  • Duplicate and repeated calls — cached or deduped away.
  • Serial waiting — replaced by parallel batches.
  • Queue-behind-slow-calls — fixed by connection ordering.
  • Cold taps — softened by prefetch and instant cached paint.

What only the backend can remove

  • The 0.4–1.5s per call the server itself takes to respond.
  • The first visit to any customer, which has no cache and must pay full latency.
  • The two-step chains (Cable TV: box ID → plan) the API forces, ~2.2s that can't be parallelized.
  • The two consistently slow endpoints — getUserAssignedItems and validateBeforeFofiBoxReg, ~1.4s each.
In short: caching makes the second visit fast; only a faster backend makes the first visit fast. The operator opening a fresh customer feels the raw server time on every screen, and that time is set entirely on the server.
05

What actually fixes it — for the backend / infrastructure team

High

Upgrade PHP 5.6 → 8.x

The single biggest available speed-up. PHP 8 adds JIT and years of engine and opcache improvements over 5.6, and closes a 7-year security gap at the same time.

High

Profile getUserAssignedItems & validateBeforeFofiBoxReg

These two are the slowest on every page that touches them (~1.4s for tiny replies) — the most likely place to find an unindexed query or a slow downstream call. Fixing them speeds up Internet, Cable TV, Fo-Fi, and Add Fo-Fi Box at once.

Medium

Collapse the Cable TV two-step into one endpoint

Have the plan endpoint accept a user ID and resolve the box server-side, so the app doesn't need the box-ID round-trip first. That removes ~1.5s from every first Cable TV / Fo-Fi load.

Medium

Move from mod_fcgid to PHP-FPM

Lower per-request process overhead, independent of the PHP version upgrade.

Medium

Re-measure after each change

The probe behind this report runs in under two minutes and lives outside the app — use it to confirm each fix actually moves the numbers before calling it done.

Methodology.

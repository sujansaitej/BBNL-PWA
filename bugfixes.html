Registration / Internet New Registration - A Portion of the Payment Amount Is Credited to the Customer's Balance Instead of Being Applied to the Subscription
Severity: High Status: Fixed Module: New Registration / Internet Payment Routes: /smartphone/crm/paynow, /smartphone/crm/payment
Issue (client-reported): A new registration completes correctly, but a portion of the payment amount is credited to the customer's Balance Amount instead of being fully applied to the subscription. Reproduced with plan 3days_plan_bbnl: the true CGST and SGST are ₹4.58 each (total tax ≈ ₹9) in both CRM and Netmon, and the printed receipt/invoice also shows ₹4.58 each. However, the PWA Payment Details screen showed CGST and SGST as ₹5.00 each. That ≈ ₹1.00 over-statement of the total surfaced as a phantom Balance Amount. The extra ₹1 was not collected on the first payment, but on the next renewal ₹1 less was debited from the operator wallet and the bill showed the old balance plus the new one (₹1 + ₹1 = ₹2), accumulating on every subsequent renewal.

Root Cause

  • The Payment Details screen (Paynow.jsx) reads the per-cycle tax from the apis/makepayment response. That endpoint returns each GST sub-tax value rounded to whole rupees — a real ₹4.58 CGST is echoed back as 5.00.
  • buildStrictInternetRenewal() trusted that rounded taxdetails.subtaxes.CGST.value / SGST.value directly, so the displayed Total Amount was inflated by ≈ ₹1 above the real invoice.
  • The actual billing engine (internet/paymentinfo + the printed receipt) bills the precise decimal (₹4.58). The ≈ ₹1 gap between the inflated PWA total and the precise invoice was recorded by the backend as a customer Balance Amount.
  • Because the displayed total fed the paidamount sent at pay time, the customer total (rounded) and the backend invoice (precise) never reconciled, so the residual was created on registration and then carried/accumulated into each renewal — eating ₹1 from the operator wallet every cycle.

Fix Summary

  • GST is now recomputed precisely from each sub-tax's own percentage against the taxable base, instead of trusting makepayment's whole-rupee value: CGST = round(taxable base × CGST% / 100, 2) (same for SGST).
  • The taxable base is read from the backend breakdown in order subtotal → planamt → plan rate, so any discount already applied by the backend is respected.
  • The precise tax values flow into both the on-screen Total Amount and the paidamount sent to savePaymentApi, so the customer total now equals the backend invoice exactly — no phantom ₹1 balance is created.
  • A safe fallback remains: if the percentage or taxable base is unavailable, the code falls back to the rounded value exactly as before, so no plan regresses.
  • Result for 3days_plan_bbnl: Payment Details now shows CGST 4.58 / SGST 4.58, the Total matches the receipt, Balance Amount stays 0.00, and the correct amount is debited from the operator wallet on every renewal with nothing accumulating.

Files Changed

  • src/pages/Paynow.jsx — added readNestedTaxPerc() and computeNestedTax(); buildStrictInternetRenewal() now derives the taxable base and recomputes CGST/SGST precisely from their percentages instead of reading the rounded makepayment tax value.
  • bugfixes.html — reset to a fresh report with this as the first fixed bug.

Renewal / Internet Second Renewal Amount Mismatch - PWA Renewal Amount Did Not Match NetMon for Newly Registered IDs
Severity: High Status: Fixed Module: Internet Renewal / Payment Routes: /smartphone/crm/payment, /smartphone/crm/paynow
Issue (client-reported): For newly registered IDs, the renewal amount shown on the PWA payment screen did not match the amount shown in NetMon, and the discrepancy was most visible on the second renewal. This is the renewal-side symptom of the same GST whole-rupee rounding defect described in the first fix above: the inflated per-cycle total (₹1 high) did not reconcile with NetMon's precise amount, and the resulting phantom balance was echoed back and carried into the next cycle, so each subsequent renewal drifted further from NetMon.

Root Cause

  • Renewals reach the same payment screen (InternetService → /payment → Paynow.jsx), and the renewal amount is computed by the same getPayDet() → buildStrictInternetRenewal() path from the apis/makepayment response.
  • apis/makepayment returns each GST sub-tax value rounded to whole rupees (e.g. ₹4.58 → ₹5.00). The PWA trusted that rounded value, so the displayed per-cycle renewal Total Amount was ≈ ₹1 higher than NetMon's precise amount.
  • Because the inflated total fed the paidamount sent at pay time, the customer total never reconciled with NetMon's precise invoice; the ≈ ₹1 gap was recorded as a balance and carried into the next cycle, so the second renewal showed the previous + new balance and diverged further from NetMon.
  • The same rounded value was used on every renewal, so the mismatch repeated and accumulated rather than self-correcting.

Fix Summary

  • Fixed at the shared root: buildStrictInternetRenewal() now recomputes each GST sub-tax precisely from its own percentage against the taxable base (round(base × perc / 100, 2)) instead of the rounded makepayment value — see the first fix for the helper details (computeNestedTax()).
  • Because the renewal screen uses this same function, the displayed renewal Total Amount now equals NetMon's precise amount on the first, second, and every subsequent renewal.
  • The paidamount sent at pay time equals the precise total, so the customer total reconciles exactly with NetMon's invoice — no phantom balance is created, nothing is carried forward, and the second renewal no longer drifts.
  • Verified with a two-renewal simulation of the renewal math: before the fix every renewal showed ₹60.85 (≠ NetMon ₹60.01); after the fix every renewal shows ₹60.01 (= NetMon) with no accumulation between renewals.

Files Changed

  • src/pages/Paynow.jsx — same shared fix as the first bug (precise GST in buildStrictInternetRenewal()); this also drives the renewal amount, so no renewal-specific code path was needed.
  • bugfixes.html — documented this renewal-side fix and its shared root cause.

FoFi FoFi Smart Box - TV MAC Address Not Displayed for Package Subscription After ATV Login on a Newly Registered ID
Severity: High Status: Fixed Module: FoFi Smart Box Routes: /smartphone/crm/customer/…/service/fofi-smart-box
Issue (client-reported): After completing a new KYC registration and logging into the Android TV (ATV) app, opening the FoFi Smart Box service did not display the TV MAC address that is needed to subscribe a package. The screen showed “Customer have not opted for this Service” with no device information, even though the Android TV had already been linked (and assigned a MAC) by the ATV login.

Root Cause

  • Logging into the ATV app links the Android TV to the customer and assigns it a MAC, but the device has no FoFi plan/expiry yet. FoFiSmartBox.jsx → isConfirmedFofiServiceDetails() only treats a device as a real FoFi service when it has both a box AND a plan/expiry.
  • During data load, when getMyPlanDetails reported “no active plan”, clearUnconfirmedFoFiService() set fofiServiceDetails = null — discarding the detected device entirely, including its Box ID and MAC. The overview then fell through to the bare “not opted” screen with no MAC shown.
  • Separately, the “Scan From TV” QR reader assumed the QR was base64-encoded JSON and required both a MAC and a serial. Android TV / Smart-TV apps present the data in other shapes (plain JSON, or a raw string, sometimes MAC-only), so the scan failed with “Invalid QR code format” / “missing MAC or serial” and the MAC never populated.

Fix Summary

  • Introduced a dedicated linkedDeviceNoPlan state. When a device is linked but has no active plan, its identity (Box ID + MAC + device type) is now preserved instead of being discarded, without marking it as a confirmed service (so the upgrade/pay flows are untouched).
  • The overview’s “not opted” branch now renders a “Linked TV Device” card showing the device type, Box ID, and TV MAC, with a hint to subscribe a package — so the operator sees the MAC immediately after ATV login.
  • When the operator proceeds (ADD FO-FI BOX → pick plan → link step), the Box ID + MAC are pre-filled from the detected device. The submit path still re-validates the device with the backend, so this is display/convenience only and cannot bypass any check.
  • Hardened “Scan From TV” parsing with parseFofiQrPayload(): it now tries base64→JSON, then plain/URL-encoded JSON, then a raw-text regex fallback for the MAC/serial, and only the MAC is required. The original native FoFi-box base64-JSON format still works exactly as before.

Files Changed

  • src/pages/services/FoFiSmartBox.jsx — added linkedDeviceNoPlan state; preserved the detected device in clearUnconfirmedFoFiService(); rendered the “Linked TV Device” card in the not-opted overview; pre-filled the link step for new users; added parseFofiQrPayload() + FOFI_SERIAL_RE and made the QR scan MAC-only and format-tolerant.
  • bugfixes.html — documented this fix.
